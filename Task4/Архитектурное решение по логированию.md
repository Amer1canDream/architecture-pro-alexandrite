# Архитектурное решение по логированию

## 1. Какие системы покрываем логированием

Логи нужно собирать из:

- Shop API
- CRM API
- MES API
- RabbitMQ consumers/producers
- Pricing Calculation Service
- Базы данных на уровне ошибок подключения и медленных запросов
- API Gateway, если он будет внедрён
- S3/file storage операции загрузки и чтения 3D-файлов

В первую очередь логирование нужно внедрить в:
1. MES API — здесь операторы видят проблемы и зависают заказы.
2. RabbitMQ-интеграции — возможна потеря сообщений.
3. Shop API — точка создания B2C-заказов.
4. CRM API — подтверждение и закрытие заказов.
5. Pricing Calculation Service — долгий расчёт стоимости.

## 3. Уровни логирования

### INFO

Используется для штатных бизнес-событий:
- заказ создан
- файл загружен
- статус изменён
- сообщение отправлено
- сообщение обработано

### WARN

Используется для нестандартных, но не критичных ситуаций:
- долгий расчёт стоимости
- повторная обработка сообщения
- превышение лимита API
- медленный запрос к БД
- временная недоступность внешней системы

### ERROR

Используется для ошибок:
- не удалось записать статус
- не удалось обработать сообщение
- ошибка чтения 3D-файла
- ошибка БД
- HTTP 500

### DEBUG

Используется только в dev/release окружениях для диагностики. В prod — выключен по умолчанию

## 4. Мотивация

Сейчас проблемы разбираются со слов клиентов. Это долго и ненадёжно. Логирование позволит команде видеть, что реально происходило с заказом внутри системы.

Логирование даст:

- быстрый поиск причины ошибки
- снижение нагрузки на поддержку
- восстановление истории заказа
- быстрый разбор инцидентов
- контроль проблемных интеграций
- основу для алертов и анализа аномалий

### Метрики, на которые повлияет логирование

1. среднее время восстановления после инцидента
2. Количество обращений в поддержку
3. Количество потерянных или зависших заказов
4. Время расследования проблем по заказу
5. Доля ошибок обработки заказов

## 5. Предлагаемое решение

### Технологии

Предлагается использовать:

- OpenSearch — хранение и поиск логов
- OpenSearch Dashboards — просмотр логов
- Fluent Bit — сбор логов из Kubernetes
- JSON structured logs — единый формат логов
- Correlation ID / Trace ID — связь логов с трейсами

---

## 6. Формат логов

Все сервисы должны писать структурированные JSON-логи

Пример:

```json
{
  "timestamp": "2026-04-26T12:00:00Z",
  "level": "INFO",
  "service": "mes-api",
  "event": "order_status_changed",
  "order_id": "ORD-123",
  "trace_id": "abc-123",
  "old_status": "MANUFACTURING_APPROVED",
  "new_status": "MANUFACTURING_STARTED",
  "operator_id": "OP-55"
}
