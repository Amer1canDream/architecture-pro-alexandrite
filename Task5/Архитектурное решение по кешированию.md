# Архитектурное решение по кешированию

## 1. Что кешируем

В первую очередь кешируем часть MES, связанную с чтением данных для операторского дашборда:

- список заказов по статусам
- список новых заказов
- агрегаты по количеству заказов в каждом статусе
- карточку заказа для чтения

Не кешируем операции записи:

- взятие заказа оператором
- изменение статуса заказа
- назначение заказа
- завершение производства
- отправку заказа

Эти операции должны сразу записываться в MES DB.

---

## 2. Мотивация

Операторы жалуются, что первая страница MES долго загружается. На ней отображается список заказов в работе по статусам. Фильтр и пагинация уже были добавлены, но проблему не решили.

Это значит, что MES DB и MES API всё равно выполняют тяжёлые операции чтения. При росте количества заказов нагрузка будет только увеличиваться.

Кеширование нужно, чтобы:

- ускорить загрузку дашборда MES
- снизить нагрузку на MES DB
- уменьшить время ожидания операторов
- быстрее показывать новые заказы
- стабилизировать MES при росте нагрузки
- уменьшить конкуренцию между чтением дашборда и записью производственных статусов

---

## 3. Предлагаемое решение

Предлагается внедрить **серверное кеширование**.

### Почему серверное, а не клиентское

Клиентское кеширование не подходит как основное решение, потому что:

- операторы должны видеть актуальные заказы
- данные общие для всех операторов
- нагрузка сейчас создаётся на MES API и MES DB
- при изменении статуса нужно централизованно инвалидировать данные

Серверное кеширование лучше, потому что:

- кеш общий для всех операторов
- снижает количество запросов к MES DB

### Технология

Для кеша предлагается использовать **Redis**.

Redis подходит, потому что:

- быстрый key-value storage
- поддерживает TTL
- распространённая технология для серверного кеша

---

## 4. Паттерн кеширования

Выбран паттерн **Cache-Aside**.

### Как работает Cache-Aside

1. MES API получает запрос на список заказов
2. MES API проверяет Redis
3. Если данные есть в кеше — возвращает их из Redis
4. Если данных нет — читает из MES DB
5. MES API сохраняет результат в Redis с TTL
6. Следующие запросы получают данные из Redis

### Почему выбран Cache-Aside

Cache-Aside подходит, потому что:

- его можно внедрить постепенно
- не нужно сразу менять всю архитектуру MES
- можно кешировать только проблемные запросы
- хорошо подходит для операций чтения
- при сбое Redis система сможет читать данные напрямую из БД

### Почему не Write-Through

Write-Through хуже подходит, потому что:

- усложняет операции записи
- при каждом изменении статуса нужно писать и в БД, и в кеш
- повышается риск ошибки синхронизации
- запись статусов должна оставаться максимально надёжной

### Почему не Refresh-Ahead

Refresh-Ahead пока не нужен, потому что:

- сложнее в реализации
- требует фонового обновления популярных ключей
- нужно заранее понимать, какие данные будут запрошены
- для MVP достаточно Cache-Aside + TTL
